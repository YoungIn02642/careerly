# CAS 직무 적합도 — 점수를 어떻게 매기고, AI 가 어디까지 하는가

CAS 2단계 상단의 **직무 적합도 1000점**에 대한 문서다. "임금직업정보시스템에 적힌
업무특성으로 내 역량 자산 점수를 낸다" 는 그 기능이다.

관련 파일

| 파일 | 하는 일 |
|---|---|
| `backend/src/wage-traits.js` | 업무특성 원자료를 임금직업정보시스템에서 받아 디스크에 캐시 |
| `backend/src/routes/casFit.js` | `POST /api/cas/fit` — 자료 조회 → AI 매칭 → 채점 호출 |
| `backend/src/cas-fit.js` | **점수 계산 엔진.** 배점·강도·등급의 단일 출처 |
| `backend/src/ai-provider.js` | Groq 호출 한 겹. 오류를 원인별로 가른다 |
| `frontend/js/cas-fit.js` | 화면. 받은 숫자를 그리기만 한다 |
| `frontend/js/db.js` | `casFit()` — 내 스펙을 실어 보낸다 / `specFingerprint()` |

## 1. 기준이 되는 자료 — 업무특성

한국고용정보원이 **재직자 설문**으로 만든 값이다. 직업 하나마다 7개 축, 축마다
항목이 있고 항목마다 0~100 점수가 붙어 있다. 이 점수는 "그 직업에서 그 항목이
얼마나 중요한가"다.

```
업무수행능력  조작 및 통제(99) · 시력(97) · 반응시간과 속도(95) …
지식          운송(95) · 지리(86) · 기계(65) …
업무활동      차량·기계·장비 작동(100) · 기계장치 제어(99) …
업무환경      움직이는 기계(100) · 마감시간(100) …
성격          신뢰성(45) · 자기통제(41) …
흥미          현실형(100) · 사회형(79)
가치관        일과 삶의 균형(59) · 사회적 공헌(56) …
```

**어디서 오나** — `wagework.go.kr` 의 비공개 AJAX 엔드포인트를 직접 부른다.

```
POST https://www.wagework.go.kr/pt/b/a/retrieveOccpNvgtChtr{Ablt|Knwg|Act|Envr|Chrc|Ints|Osv}Data.do
body   : konetOccpCd=<KECO 직업코드>
헤더   : X-Requested-With: XMLHttpRequest   ← 없으면 JSON 대신 HTML 이 온다
응답   : { data: { ipcrQtntList: [{ qsnrNm, qsnrCn, cnt }] } }
         qsnrNm 항목명 · qsnrCn 설명 · cnt 점수(0~100, 문자열로 온다)
```

**미리 다 받지 않는다.** 직업 461개 × 축 7개 = 3,227회다. 학생 한 명이 보는 직업은
한둘이라, **고른 직업만 그때 받아** `backend/data/wage-traits/<직업코드>.json` 에
캐시한다. 두 번째부터는 외부 호출이 0이다.

축 하나가 실패해도 나머지로 간다. 하나도 못 받으면 캐시하지 않고(다음에 다시 시도)
화면은 503 `no-traits` 안내를 낸다.

**채점에는 축마다 상위 5항목만 쓴다**(`topTraits(raw, 5)`). 전부 넣으면 프롬프트가
길어져 뒤쪽 규칙이 잘린다. 즉 실제로 채점 대상이 되는 항목은 최대 35개다.

> 전제 조건: **직업(KECO 직업코드)까지 골라야** 계산된다. 2차 분류만으로는 안 된다 —
> 업무특성은 직업 단위 자료다. 로드맵에서 직업을 안 골랐으면 화면은 채점 대신
> "직업을 고르면 적합도를 계산해요" 를 낸다.

## 2. 역할 분담 — AI 는 매칭만, 점수는 코드가

이 저장소의 원칙이다(작업정리 6장·9장). 세 단계로 나뉜다.

```
1단계  업무특성 가져오기   wage-traits.js      외부 API + 디스크 캐시
2단계  매칭               AI (Groq)           "내 활동 A 가 업무특성 B 를 뒷받침하는가"
3단계  채점               cas-fit.js          점수는 여기서만 나온다
```

**모델이 총점을 말해도 쓰지 않는다.** 시스템 프롬프트에 그렇게 박아 두었다.

```
**점수를 매기지 마라.** 총점·백분율·등급을 쓰지 마라 — 그건 우리 코드가 계산한다.
너는 "이 활동이 이 특성을 뒷받침하는가" 와 그 근거만 답한다.
```

이유는 두 가지다. 같은 입력이면 같은 점수가 나와야 하고, 항목마다 왜 그 점수인지
짚을 수 있어야 한다. 모델에 총점을 맡기면 둘 다 깨진다.

### AI 가 받는 것

- 직업 이름
- 업무특성 35항목 (축 이름 · 항목 이름 · 중요도 · 설명)
- 내 스펙을 줄로 편 것 — 전공 계열 / 학점 / 어학 / 자격증 / 활동(이름·종류·기간·역할·성과)

없는 필드는 **아예 안 넣는다.** '없음' 이라고 채워 보내면 모델이 그 '없음' 을
근거로 쓴다(자소서 초안에서 겪었다).

### AI 가 내놓는 것

```json
{"matches":[{"axis":"ability","trait":"조작 및 통제","strength":2,
             "evidence":"로봇 동아리에서 제어 장비를 다뤘습니다","from":"로봇 동아리"}]}
```

`strength` 는 뒷받침하는 정도다.

| 값 | 뜻 |
|---|---|
| 3 | 그 일을 직접 해 본 경험이 있다 |
| 2 | 비슷한 일을 했거나 자격·전공으로 뒷받침된다 |
| 1 | 스쳐 지나간 수준이다 |
| (없음) | 근거가 없다 → 넣지 않는다. 우리가 "아직 못 채웠다" 로 다룬다 |

**4단계인 이유** — 0/1 이면 "조금 해봤다" 를 표현할 수 없고, 10단계면 모델이 3과 4를
일관되게 구분하지 못한다(실측: 같은 입력에 3↔5 가 오갔다).

### 모델 응답을 그대로 믿지 않는다

`parseMatches()` 가 두 겹으로 거른다.

1. **우리가 아는 축·항목 이름만 남긴다.** 모르는 것은 버린다 — 지어낸 것일 수 있다.
2. 모델이 항목 이름을 살짝 바꿔 오는 일이 있어(띄어쓰기·조사), **공백을 지운 형태로도**
   맞춰 본다. 안 맞추면 채점에서 조용히 빠진다.
3. `strength` 는 0~3 으로 clamp, `evidence` 200자·`from` 80자로 자른다.

### 모델 설정

| 항목 | 값 | 이유 |
|---|---|---|
| 프로바이더 | Groq **전용** | 기본값이 로컬(Ollama)이면 env 가 안 읽힐 때 조용히 로컬로 떨어져, 쓰지도 않는 도구의 오류가 사용자 화면에 뜬다. 실제로 그 사고가 났다 |
| 모델 | `.env` 의 `GROQ_MODEL` (현재 `openai/gpt-oss-120b`) | 모델 폐기 시 코드 수정 없이 갈아끼우려고 |
| temperature | 0.2 | |
| response_format | `json_object` | |
| max_tokens | **4000** | 추론형 모델이라 답을 쓰기 전에 토큰을 먼저 쓴다. 1400 으로 잡았더니 추론에 다 쓰고 JSON 이 중간에 잘려 Groq 의 검증에 튕겼다(같은 프롬프트가 4000 에서는 매칭 11건) |
| reasoning_effort | `low` (추론 모델일 때만) | 같은 이유. 추론을 안 쓰는 llama 계열에 보내면 거절당하므로 모델 이름으로 가른다 |
| 타임아웃 | 60초 (`CAS_AI_TIMEOUT_MS`) | |

## 3. 채점 — `cas-fit.js`

### 3-1. 축별 배점 (합 1000)

| 축 | 배점 | 왜 |
|---|---:|---|
| 업무수행능력 `ability` | 260 | 활동·자격증·수업으로 **증명할 수 있다** |
| 지식 `knowledge` | 240 | 〃 |
| 업무활동 `activity` | 200 | 〃 |
| 업무환경 `env` | 120 | 겪어 봤는지가 드러난다(실외·교대·마감) |
| 성격 `character` | 80 | 적성 검사의 영역. 스펙으로 증명되지 않는다 |
| 흥미 `interest` | 60 | 〃 |
| 가치관 `value` | 40 | 〃 |

성격·흥미를 무겁게 잡으면 "성실합니다" 같은 자기 주장이 점수가 된다. CAS 가 처음부터
피하려던 것이다.

**축이 통째로 없으면 그 배점을 남은 축에 나눠 준다.** 빈 축을 0점으로 두면 자료가
부족한 직업일수록 점수가 낮아지는데, 그건 사람의 적합도가 아니라 데이터의 문제다.

```js
scale = 1000 / (자료가 있는 축들의 배점 합)
축 배점 = WEIGHTS[축] × scale
```

### 3-2. 강도 → 채운 정도

```js
STRENGTH  = { 0: 0, 1: 0.35, 2: 0.7, 3: 1 }
BASE_FLOOR = 0.15
filled = clamp01( max(STRENGTH[강도], BASE_FLOOR) )
```

**`BASE_FLOOR` 가 있는 이유** — 0을 주면 신입은 거의 모든 항목이 0이라 총점이 바닥에
붙고, 화면이 "당신은 이 직업에 안 맞습니다" 로 읽힌다. 실제로는 **아직 증명하지
못했을 뿐**이라 그 차이를 점수에 담는다. 그래서 근거가 하나도 없어도 총점은
**150점(15%) 언저리**가 나온다 — 0점이 아니다.

### 3-3. 한 축의 점수 — 중요도로 가중

```js
max = Σ 항목의 중요도
got = Σ (항목의 중요도 × filled)
축 점수 = 축 배점 × (got / max)
```

**중요도로 가중하는 것이 핵심이다.** 버스운전원의 '조작 및 통제(99)' 와
'경제와 회계(59)' 를 같은 무게로 세면 직업의 성격이 사라진다.

### 3-4. 총점·등급

축 점수를 다 더하고 **마지막에 한 번만** 반올림한다(축마다 반올림하면 합이 1000을
넘거나 모자란다).

| 백분율 | 등급 |
|---|---|
| 85 이상 | 매우 적합 |
| 70 이상 | 적합 |
| 50 이상 | 보통 |
| 그 미만 | 준비 필요 |

### 3-5. "무엇부터 채우면 오를까" — gaps

점수만 보여주면 학생이 할 수 있는 일이 없다. 못 채운 항목을 **손실이 큰 순**으로
6개 뽑는다.

```js
loss = 항목 중요도 × (1 - filled) × (축 배점 / 1000)
```

축을 가로질러 섞는다 — 학생은 축 단위로 움직이지 않고, "무엇부터 할까" 한 줄이면
된다.

### 3-6. 계산 예시

`ability` 축(배점 260), 5항목이 중요도 99·97·95·88·80(합 459)이라 하자.
'조작 및 통제(99)' 에 강도 2, 나머지는 근거 없음이면

```
got = 99×0.7 + 97×0.15 + 95×0.15 + 88×0.15 + 80×0.15
    = 69.3 + 54.0 = 123.3
축 점수 = 260 × (123.3 / 459) = 69.8점  (만점 260)
```

근거가 하나도 없었다면 `459 × 0.15 = 68.85` → `260 × 0.15 = 39점`. 즉 강도 2짜리
근거 하나가 이 축에서 약 31점을 만들었다.

## 4. AI 가 죽어도 화면은 산다

이게 이 기능의 설계 전제다. 매칭이 비면 **모든 항목이 `BASE_FLOOR`** 로 채점되고,
점수는 낮게 나오지만 축별 점수도 gaps 도 그대로 나온다. 다만 **왜 근거가 없는지**는
반드시 알려 준다 — 조용히 낮은 점수를 주면 사용자가 오해한다.

`notice` 는 세 갈래다.

| 상황 | 화면에 뜨는 말 |
|---|---|
| 스펙이 없다 | 스펙을 입력하면 내 활동과 업무특성을 맞춰 점수를 냅니다. |
| AI 가 실패했다 | 근거를 못 붙여 바닥 점수로 계산했어요 — *(원인별 문장)* |
| 정상 | (없음) |

### 실패 원인은 뭉개지 않는다

`ai-provider.js` 가 상태코드별로 문장을 가른다. 사용자가 할 일이 다르기 때문이다.

| 상태 | 원인 | 사용자가 할 일 | 다시 눌러서 될까 |
|---|---|---|---|
| 429 | **Groq 무료 쿼터 초과** | 잠시 뒤 다시 | ✅ |
| 504 | 60초 안에 응답 없음 | 잠시 뒤 다시 | ✅ |
| 502 | 그 밖의 호출 실패 | 잠시 뒤 다시 | ✅ |
| 503 | `GROQ_API_KEY` 오타·누락 / 폐기된 `GROQ_MODEL` | `.env` 를 고쳐야 한다 | ❌ |

**429 가 압도적으로 흔하다.** 실측: 같은 요청을 연달아 6번 보내면 1번이 429다.
업무특성 35항목 프롬프트에 `max_tokens 4000` 이라 무료 티어의 분당 토큰 한도를
금방 친다. `groq-sdk` 가 `maxRetries: 1` 로 한 번은 자동 재시도하는데, 그래도
남으면 사용자에게 나간다.

화면은 **다시 눌러서 되는 실패(429·502·504)에만 "다시 시도" 버튼**을 만든다.
키 오타나 폐기된 모델은 몇 번을 눌러도 같으므로 버튼을 만들지 않는다 — 되지도 않는
버튼을 주면 사용자가 원인을 찾는 대신 계속 누른다.

## 5. 캐시 — 언제 다시 부르나

매칭은 AI 호출이라 탭을 옮길 때마다 부르면 느리고 무료 쿼터가 샌다. 그래서 화면이
결과를 담아 둔다. 캐시 키는

```js
`${직업코드}|${DB.specFingerprint()}`
```

`specFingerprint()` 는 `casFit()` 이 **서버로 실제로 보내는 필드**(전공·학점·어학·
자격증·활동)로 만든다. 둘 중 하나라도 바뀌면 다시 부른다.

> **여기서 났던 버그** — 예전에는 캐시 키가 **직업 코드뿐**이었다. 그래서 스펙을
> 새로 넣어도 직업이 그대로면 다시 부르지 않았고, 스펙이 없던 시절에 계산한
> '아직 근거 없음' 이 계속 떴다. 저장은 됐는데 화면만 안 바뀌는 것이라 사용자에게는
> 채점이 통째로 고장난 것으로 보인다.
>
> 이 지문에 없는 필드를 `casFit()` 이 보내기 시작하면 그 변화는 캐시를 못 깨운다 —
> `casFit()` 을 고칠 때 `specFingerprint()` 도 같이 고친다.

수동 무효화는 두 군데다.

- `CASFit.reset()` — 로드맵에서 직무를 바꿀 때 (`cas-hero.js`)
- "다시 시도" 버튼 — 실패한 결과를 들고 갇히지 않게 하는 통로

## 6. 이 점수를 아래 '선배 비교' 와 섞어 읽지 않는다

같은 화면에 있지만 다른 질문에 답한다.

| | 묻는 것 | 기준 | 선배가 0명이면 |
|---|---|---|---|
| **직무 적합도** (이 문서) | 이 일에 내가 맞나 | 임금직업정보시스템 업무특성 | 그래도 답이 나온다 |
| 레이더·스펙 비교·부족 항목 | 같은 길을 간 사람들 사이에서 내가 어디쯤인가 | 선배 데이터 | 답을 못 한다 |

예전 CAS 는 후자뿐이었고, 표본이 적은 직무에서 가장 자주 막혔다. 기준을 업무특성으로
바꾼 것이 이 기능이다.

## 7. 손댈 때 주의

- **배점·강도·등급을 화면에서 다시 계산하지 않는다.** `cas-fit.js` 가 단일 출처다.
  프론트는 받은 숫자를 그리기만 한다.
- **업무특성 캐시는 갱신 로직이 없다.** 원자료가 바뀌면
  `backend/data/wage-traits/<코드>.json` 을 지워야 다시 받는다.
- 새 축을 추가하면 `wage-traits.AXES` 와 `cas-fit.WEIGHTS` 를 **함께** 고친다.
  한쪽만 고치면 배점 합이 1000이 아니게 되고, 에러 없이 점수만 조용히 틀어진다.
- 테스트는 저장소 루트에서: `node test/cas-fit.test.js`
