# 2차 배포 — 무엇을 어디서 어떻게 고치나

1차 배포 뒤 나온 수정사항을 **"어느 파일·어느 콘솔에서 무엇을 하는지"** 로 정리한 문서.
항목 선정과 우선순위의 근거는 `CAREERLY-작업정리.md` 14장에 있고, 이 문서는 그것을
**실행 단위**로 풀어 쓴 것이다.

- 배포 절차 자체(dev → main, 검증 순서, 롤백): `docs/배포.md` **9장**
- 개발환경 셋업·브랜치 규칙: `docs/팀-개발환경.md`
- 화면 코드가 어디 있는지: `docs/화면-구조-지도.md`

**작업 단위 = 브랜치 하나 = PR 하나.** 아래 표의 "브랜치" 열 이름을 그대로 쓴다.

## 1. 코드로 고치는 것

### C1. 멘토 '받은 요청' 서버 연동 — **최우선**

> 브랜치 `feature/b16-mentor-requests` · 작업정리 B16

**증상**: 멘티가 보낸 신청은 DB(`mentoring_requests`)에 들어가는데 **멘토 화면은
`localStorage` 만 본다.** 실제로는 멘토가 신청을 영영 못 받는다. 배포된 상태에서
티가 나는 유일한 미완성 지점이다.

**어디**

| 파일 | 무엇 |
|---|---|
| `backend/src/routes/mentoring.js:48` | `GET /requests` 가 `WHERE mentee_id=?` 하나뿐이다. 멘토로 로그인했으면 `mentor_id` 로 조회하는 갈래를 추가한다 |
| `backend/src/routes/mentoring.js` | 수락·거절 라우트가 **없다.** `POST /requests/:id/accept` · `/reject` 를 만든다. 소유자 확인은 `cancel`(:89) 과 같은 모양으로 |
| `frontend/js/mentoring.js:257,966~1000` | `STATE.received` 시드와 `renderReceived()`·수락/거절 핸들러가 전부 로컬 배열을 직접 자른다(`splice`). 멘티 쪽(`'내가 신청'`)을 서버로 옮긴 방식과 똑같이 서버 응답을 그리도록 바꾼다 |

**먼저 정해야 할 것 (막히는 지점)**: 지금 `mentor_id` 는 **프론트 `MENTORS` 시드
배열의 id 이지 회원 id 가 아니다.** 라우트 머리주석에도 "멘토가 실제 회원이 되면
여기서 `db.users` 를 조회하도록 바꾼다" 고 적혀 있다. 그래서 이 작업은 둘 중 하나다.

1. **멘토를 회원으로 승격** — 가입 시 역할이 `mentor` 인 사용자를 멘토 목록에 노출하고
   `mentor_id` 를 `users.id` 로 쓴다. 정공법이지만 멘토 목록·상세 화면까지 건드린다
2. **시드 멘토에 계정을 매핑** — 시드 멘토 id ↔ 회원 id 매핑을 두고 그 계정으로
   로그인했을 때만 받은 요청을 보여준다. 범위가 작고 되돌리기 쉽다

**2번으로 시작하고 1번은 별도 PR 로 미루는 것을 권한다** — 2차 배포에서 필요한 것은
"멘토가 신청을 받는다" 이지 "멘토 회원제" 가 아니다.

**검증**: 스테이징에서 멘티 계정으로 신청 → 멘토 계정으로 로그인 → 목록에 뜨는지 →
수락 → **브라우저를 새로고침해도 유지되는지**(로컬이면 여기서 티가 난다) →
**다른 기기/시크릿창에서도 보이는지**.

### C2. 희망직무 다중선택

> 브랜치 `feature/b14-job-chips` · 작업정리 B14

`frontend/js/spec-form.js:1336` `fillFieldJob()` 이 `<select>` 단일 선택으로 채운다.
chip 다중선택으로 바꾸고, 저장 형식(`spec.job`)이 배열이 되므로 **읽는 쪽을 같이
찾아 고친다** — `cas.js`·`recommendations`·통계에서 `spec.job` 을 문자열로 가정하는
자리가 있다. **DB 컬럼 형식이 바뀌면 스키마 변경 항목이라** 배포 순서를 지켜야 한다
(`docs/배포.md` 9장 2번).

> ⚠️ 여기서 13-5 의 함정을 다시 밟기 쉽다: **JS 로 `select.value` 를 바꿔도 `change`
> 이벤트는 나지 않는다.** 값을 코드로 바꾼 뒤에는 의존하는 갱신을 직접 호출한다.

### C3. `job-trends` 를 NCS → KECO 로 이전

로드맵은 KECO 로 옮겼는데 트렌드만 NCS 분류로 남아 있다.

**테스트를 먼저 고치고 구현을 맞추는** 편이 안전하다.

### C4. 스펙 입력 placeholder 정리

> 브랜치 `feature/b3-placeholder` · 작업정리 B3

`frontend/js/spec-form.js` 의 `placeholder` 문구들(144·150·180·201·234행 등).
가장 가벼운 작업이라 새 팀원의 **첫 PR 연습용**으로 적합하다.

### 미루는 것

**B13(CAS 점수표 재설계)** — 회의 메모의 숫자는 "(가중치 예시)" 였다. **배포 후 실제
데이터를 모은 뒤** 손대는 게 맞다. 지금 건드리면 근거 없는 숫자를 근거 없는 숫자로
바꾸는 일이 된다. 배점을 고칠 때는 반드시 `frontend/js/cas.js` 한 곳만 고친다 —
**모든 배점 상수의 단일 출처**이고 백엔드도 여기서 읽는다.

## 2. 콘솔에서 고치는 것 (코드 아님 — 사용자가 웹에서)

### K1. 네이버 로그인 '개발 중' 상태 — **지금 막혀 있음**

**증상**: 다른 사람이 네이버 로그인을 누르면
`현재 careerly는 개발 중 상태입니다. 개발 중 상태에서는 등록된 아이디만 로그인할 수 있습니다.`

**원인**: 코드·키·콜백 문제가 아니다. 네이버 로그인 앱은 만들면 **'개발 중'** 상태로
시작하고, 그 상태에서는 **개발자 본인 + 콘솔에 등록한 테스터**만 로그인된다.
(운영 서버가 올바른 `client_id`·`redirect_uri` 로 `nid.naver.com` 에 보내는 것은 확인했다.)

**조치**

| 급한 것 | 네이버 개발자센터 → 내 애플리케이션 → C:road → **API 설정 → 멤버관리**에 팀원의 **네이버 아이디**를 추가한다. 최대 10명, 즉시 적용 |
|---|---|
| 공개하려면 | 같은 화면에서 **검수 요청** → '서비스 중' 전환. 제공받는 항목마다 사용 목적을 적어야 한다(C:road: 이메일=계정 식별, 이름/닉네임=화면 표시). 서비스 URL·로고·**로그인 버튼이 보이는 화면 캡처**가 필요하고 며칠 걸린다 |

> **카카오도 성격이 같은 함정이 있다.** 비즈니스 앱 전환 전에는 항목이 제한되고
> 팀원 계정은 앱 '팀원' 으로 등록돼 있어야 한다. **다른 사람 계정으로 한 번
> 눌러보게 해서** 같은 종류의 벽이 없는지 확인할 것.

### K2. 결제 전 과정 확인 (작업정리 A5)

`TOSS_SECRET_KEY` 는 **승인 단계에서만** 쓰인다. 밖에서 curl 로는 검증할 수 없다.
멘토 신청 → 결제창 → **테스트 카드 승인까지** 한 번 통과시켜야 그 키가 맞는지 안다.
스테이징이 생기면 거기서 한다.

### K3. 운영 DB 비밀번호 교체 (작업정리 A7)

셋업 중 대화에 노출됐다. Railway MySQL 서비스에서 교체한다. 앱은
`${{MySQL.MYSQL_URL}}` 참조를 쓰므로 **앱 변수는 자동으로 따라간다.**
교체 뒤 **로컬에 저장해 둔 `MYSQL_PUBLIC_URL` 메모도 같이 갱신**해야 스크립트가 돈다.

### K4. 토스 라이브 키 (작업정리 A6)

실제 결제를 받을 때만. `test_ck_` → 라이브 키 교체 + **사업자 심사**가 필요하다.
2차 배포 범위 밖일 가능성이 높다.

### K5. 남은 API 승인 대기

## 4. 2차 배포 전 마지막 점검

```bash
# 저장소 루트에서
for f in test/*.test.js; do node "$f" | tail -1; done     # 합 227 통과
git status --porcelain                                     # 비어 있어야 한다
```

그다음 **스테이징 도메인**에 `docs/배포.md` 6장의 curl 점검을 돌리고, 브라우저에서:

1. 네이버·카카오 로그인 → 추가입력 화면 (K1 조치 후 **팀원 계정으로도**)
2. 스펙 입력 → 저장 → 다시 열었을 때 그대로인지
3. **멘티 신청 → 멘토 계정에서 받은 요청 확인 → 수락** (C1 의 핵심)
4. 결제창 승인까지 (K2)

전부 통과하면 `dev` → `main` PR. 이후는 `docs/배포.md` 9장 그대로.

> **`Redeploy` 를 누르지 않는다.** 그 배포의 옛 커밋이 다시 올라간다.
> 코드를 바꿨으면 푸시 이벤트 또는 `Deploy latest commit`.

## 5. 새 항목이 생기면

**여기에 먼저 적는다.** 형식은 위와 같이 `증상 → 어디(파일·행) → 조치 → 검증` 넷이다.
"어디" 를 못 적겠으면 그건 아직 조사가 안 끝난 것이다 — 그 상태로 브랜치를 파면
PR 이 커진다. 조사만 먼저 하고 결과를 이 문서에 적는다.

작업이 끝나 배포까지 나간 항목은 이 문서에서 지우고 **`CAREERLY-작업정리.md` 에
기록을 남긴다** — 이 문서는 '할 일', 작업정리는 '한 일과 그 이유' 다.
